# Redis 架构分析报告

## 1. 核心矛盾与存在意义 (The "Why")

### 痛点还原

在没有 Redis 之前，开发者面临什么样的"灾难"？

- **传统数据库太慢**：磁盘 I/O 是内存的 1000 倍以上，每次访问数据库都像"等公交车"
- **数据结构受限**：MySQL/PostgreSQL 只有表、行、列，想存个列表、集合、排行榜？自己序列化去
- **并发连接瓶颈**：每个客户端一个线程？服务器直接爆炸
- **简单功能复杂化**：实现一个计数器要加锁、读出、加1、写回...10行代码起步

### 一句话定义

**Redis = 把数据存在内存里的"瑞士军刀"式数据结构服务器，用单线程事件循环 + IO 多路复用实现超高并发**

它只用一个核心概念就解决了上述所有问题：**把复杂数据结构直接存到内存里，用简单命令操作它们**。

### 适用场景

**必须用 Redis 的场景**：
- 缓存热点数据（访问频率 > 10次/秒）
- 实时计数器（点赞、浏览量、限流）
- 会话存储（用户登录态）
- 消息队列（Pub/Sub、Stream）
- 分布式锁

**杀鸡用牛刀的场景**：
- 大数据分析（几亿条数据的复杂 join）
- 文件存储（应该用对象存储如 S3）
- 长期归档（应该用数据库 + 冷存储）

## 2. 静态架构解剖 (The "Static Structure")

识别出 Redis 最核心的模块：

| 模块名称 | 核心职责 | 复杂度 | 核心地位 |
| :--- | :--- | :--- | :--- |
| **server.c / server.h** | 整个服务器的老大，管理全局状态、配置、命令表 | 高 | 灵魂 |
| **ae.c** | 事件循环心脏，驱动整个服务器的"心跳" | 高 | 灵魂 |
| **networking.c** | 处理客户端连接、读写网络数据、协议解析 | 高 | 骨架 |
| **dict.c** | 哈希表实现，存储所有 key-value 的核心数据结构 | 中 | 骨架 |
| **db.c** | 数据库操作封装，提供 SELECT、FLUSHDB 等命令 | 中 | 皮肉 |
| **replication.c** | 主从复制，Redis 高可用的基石 | 高 | 骨架 |
| **cluster.c** | 集群分片，让 Redis 可以横向扩展 | 高 | 皮肉 |
| **aof.c / rdb.c** | 持久化，把内存数据写入磁盘 | 中 | 皮肉 |

### 核心数据结构：redisServer

`server.h:1917` 定义了 Redis 服务器的核心结构体：

```c
struct redisServer {
    // 事件循环 - 整个服务器的动力源泉
    aeEventLoop *el;

    // 数据库数组 - 最多 16 个 DB
    redisDb *db;

    // 命令表 - 所有命令的注册表
    dict *commands;

    // 客户端列表
    list *clients;
    list *slaves;  // 从节点

    // 持久化相关
    int aof_state;
    // ...
};
```

## 3. 动态核心链路追踪 (The "Dynamic Flow")

### 典型场景：执行一个 `GET key` 命令

```
客户端 ──TCP连接──> ae 事件循环 ──读取──> networking ──解析──> 命令分发 ──查找key──> dict ──返回value──> 客户端
```

### 关键数据流转

| 阶段 | 数据变化 | 涉及模块 |
| :--- | :--- | :--- |
| 1. 连接 | `fd` → `client*` | anet.c, networking.c |
| 2. 读取 | `字节流` → `query buffer` | networking.c |
| 3. 解析 | `原始数据` → `redisObject* cmd[]` | resp_parser.c |
| 4. 查找 | `cmd字符串` → `redisCommand*` | server.c |
| 5. 执行 | `key字符串` → `redisObject* value` | db.c, dict.c |
| 6. 返回 | `value` → `RESP协议字节` | networking.c |

## 4. 架构评价 (The Trade-off)

### 设计亮点

**单线程事件循环 + IO 多路复用 = 性能怪兽**

Redis 选择了"单线程 + 非阻塞 + 多路复用"这个看似反直觉的设计，却成就了传奇性能：

- **避免锁竞争**：单线程天然不需要考虑并发安全问题
- **超高并发**：一个线程管理成千上万个连接（epoll/kqueue）
- **简单可靠**：没有复杂的线程同步 bug

> 但 Redis 8.0 引入了 **IO Threads**，开始支持多线程处理网络 I/O，但核心命令执行仍然是单线程。

### 潜在代价

**内存即一切**

- **内存上限**：所有数据必须放在内存，受限于物理内存大小
- **持久化开销**：RDB 快照会阻塞，AOF 写操作有 I/O 开销
- **单线程局限**：无法利用多核 CPU（可通过多实例解决）

**解决方案**：
- Redis Cluster 分片存储
- 内存淘汰策略（LRU、LFU）
- 混合持久化（RDB + AOF）

---

## 总结

Redis 之所以能成为"几乎每个互联网公司都在用"的基础设施，核心在于：

1. **用内存换速度**：内存比磁盘快 1000 倍以上
2. **用简单换可靠**：单线程避免了 90% 的并发 bug
3. **用数据结构换生产力**：String、List、Set、Hash、Sorted Set、Stream... 开发者直接用，不需要自己实现

这可能就是"大道至简"的最好诠释。
